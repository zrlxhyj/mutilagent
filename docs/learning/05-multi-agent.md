# 05：多智能体协作与框架分工

[上一章](04-tools.md) · [目录](README.md) · [下一章](06-agent-runtime.md)

## 1. 从单个 Agent 到多个角色

单个 Agent 可以同时拥有搜索、查库和写文件工具。任务增多后，它需要同时记住很多规则，工具范围也越来越大。拆分子智能体可以把专门任务集中到更小的角色和工具集合中。

本项目采用主智能体统一委派的方式：主智能体负责判断需要哪些信息，子智能体负责相应信息获取，主智能体最后汇总。这种结构常被称为 orchestrator 或 supervisor 模式。

名称不是重点。要问：谁拥有最终任务目标；谁决定分工；数据如何返回；错误由谁处理。

## 2. 子智能体配置逐项理解

[网络助手配置](../../agent/subagents/network_search_agent.py)：

```python
network_search_agent = {
    "name": sub_agents_content["tavily"]["name"],
    "description": sub_agents_content["tavily"]["description"],
    "system_prompt": sub_agents_content["tavily"]["system_prompt"],
    "tools": [internet_search],
}
```

`name` 用于标识角色；`description` 描述适用任务；`system_prompt` 指导执行；`tools` 传入实际工具对象。`tools` 不是工具名字字符串列表，框架需要可调用对象及相关元信息。

字典只是声明。创建智能体、组织消息、执行工具等由框架完成。当前配置没有为各子智能体设置独立 model；不能据此声称运行着三个不同的模型服务。

官方文档介绍了 description、system_prompt 和 tools 的配置方式：[子智能体文档](https://docs.langchain.com/oss/python/deepagents/subagents)。文档中的新版本字段应先核对 0.4.3 是否支持。

## 3. 主智能体的组装

当前 `create_main_agent(checkpointer)` 把 model、system_prompt、三个文件工具、checkpointer 和三个子智能体一起交给 `create_deep_agent`。

把创建逻辑放在函数里，调用方可以决定什么时候提供持久化资源。当前服务在启动生命周期内创建，而不是模块导入时就创建异步 SQLite 连接。

一个模块级 `main_agent` 对象可以服务多个运行请求；每个请求通过配置和状态区分。但“共享对象”不自动证明所有自定义工具和全局资源都并发安全，需要逐层检查。

## 4. 委派在项目里怎样体现

`run_deep_agent` 遇到工具名为 `task` 的调用时，读取 `subagent_type` 和 `description`，上报正在调用助手。

教学示意：

```json
{
  "name":"task",
  "args":{
    "subagent_type":"市场情报助手",
    "description":"查询某品类变化，返回有日期和来源的事实。"
  }
}
```

`description` 在这里是一次具体委派任务的描述，与角色配置中的长期岗位简介虽然同名，但作用层次不同。

真正执行子智能体的是框架；这段业务代码主要观察并上报委派事件。不要误以为 `monitor.report_assistant` 执行了子智能体。

## 5. 一次合理的任务拆分

问题：“结合 2026 年上半年销售和市场变化，给出下半年建议。”

主智能体可以委派：

| 子任务       | 应提供的输入                 | 期望返回                       |
| ------------ | ---------------------------- | ------------------------------ |
| 查询销售     | 时间范围、订单状态、目标指标 | 数值、口径、SQL 或字段依据     |
| 查询市场     | 品类、地区、时间范围         | 来源、日期、事实、限制         |
| 查询内部复盘 | 品类、相关经营问题           | 文档依据、已采取措施、结论范围 |

最终汇总要区分“数据库显示的事实”“市场资料给出的解释线索”“尚待验证的因果假设”。多条线索同时出现不能自动证明因果关系。

## 6. 委派不等于自动共享全部信息

不要假设子智能体知道主智能体所有历史。委派信息需要包含完成子任务所需的目标、时间范围、输出要求与必要背景。

子智能体返回过度概括的结论，主智能体可能丢失证据；返回全部原文又可能占用太多上下文。一个折中接口是“简短结论 + 关键事实 + 来源 + 不确定性 + 必要原始片段”。

具体上下文隔离、继承和状态配置取决于框架版本及构造方式，本项目没有显式定义助手之间直接互传消息的业务逻辑。

## 7. 多智能体何时值得使用

当任务具有明显的专业边界、工具权限差异或独立的上下文需求时，拆分更容易管理。若只有“搜一条事实然后回答”，新增角色可能只增加一次委派和额外模型调用。

成本粗略看为所有模型调用成本之和，再加外部工具服务成本。总耗时受顺序依赖、并发安排、模型延迟和工具延迟影响。三个角色不等于固定三次调用，也不等于耗时缩短到三分之一。

需要先拿到数据库商品名称才能搜索竞品，这两步有依赖；独立的地区市场检索才可能并发。并发安排必须尊重依赖和服务限制。

## 8. 规划、反思和人工审批

规划是把目标拆成任务；反思是检查已有结果是否满足目标；人工审批用于需要人判断或授权的步骤。它们都需要明确触发条件和退出条件。

当前提示词要求复杂任务规划，但仓库没有独立实现“审阅者 Agent 反复检查直到通过”的完整闭环，也没有业务层人工审批流程。后续可以加入，但应先定义“通过”的可验证标准，避免无止境自我修改。
