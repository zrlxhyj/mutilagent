# 13：可靠性、安全、评估与工程改进

[上一章](12-setup-debug.md) · [目录](README.md) · [下一章](14-exercises.md)

## 1. 从“能演示”到“能稳定使用”

一个任务偶尔成功只能证明存在成功路径。可靠系统需要知道失败会怎样发生，如何限制损失，如何恢复，怎样确认结果符合目标。

本章的改进均为建议，没有在本次编写中自动修改业务源码。

## 2. 当前实现核对表

| 观察位置 | 可确认的现状 | 改进方向 | 验收证据 |
|---|---|---|---|
| create_main_agent | 始终注册三个业务子智能体 | 按配置启用服务并给出状态 | 缺少 RAG 配置仍可运行搜索路径 |
| run_task | create_task 后未维护运行表 | 保存任务句柄和终态 | 可查询、取消指定运行 |
| run_deep_agent | 前置文件准备在主要 try 外 | 覆盖整个任务生命周期 | 复制失败也有明确 error 终态 |
| ConnectionManager | 每 ID 单个连接，内存保存 | 多订阅/断线恢复策略 | 重连可获取已完成结果 |
| 路径工具 | 可接受部分会话外路径 | 统一目录边界校验 | 越界请求被拒绝 |
| SQL 工具 | 任意 SQL 直接执行 | 只读账号、表与语句限制 | 非读取操作无法执行 |
| 文件接口 | output 级路径检查 | 用户与会话归属校验 | A 无法读 B 的文件 |
| 日志 | 多为开始与最终结果 | 增加工具结束、耗时、错误类别 | 能区分模型慢和工具慢 |
| 提示词 | 次数与顺序主要靠指令 | 代码预算与必要状态约束 | 超额调用被阻止 |
| 页面 | 每次新 ID、结果截断展示 | 追问入口和完整结果查看 | 同 ID 第二轮延续可验证 |

## 3. 明确运行状态机

建议定义：queued → running → succeeded / failed / cancelled。终态应尽量只有一个，并明确谁负责写入。

thread_id 表示会话，run_id 表示一次运行，tool_call_id 表示一次工具请求。把三个层次分开后，更容易解释“同一会话的第二次任务失败，但第一次报告仍存在”。

当前项目没有这套完整状态机。前端的 running/done/error 是展示状态，不能代替后端可靠运行记录。

## 4. 超时与预算

至少区分：单次模型请求超时、单次工具超时、重试预算、整个任务时限、最大模型轮数、最大工具次数、最大输入/输出长度。

一个工具超时 30 秒、重试四次，整个任务可能远超 30 秒。多个子智能体各自重试还会叠加。预算要计算整个调用链，而不是只盯一个参数。

增加限制时应返回可理解的停止原因，例如“已达到搜索次数限制，当前基于三条可用来源回答”，而不是假装任务完全完成。

## 5. 失败分类

| 类型 | 例子 | 合适处理 |
|---|---|---|
| 输入问题 | 缺时间范围、无效文件名 | 校验或请求补充 |
| 配置问题 | 缺密钥、错误数据库名 | 明确失败并定位配置 |
| 暂时故障 | 连接中断、服务短暂过载 | 有上限的重试 |
| 权限问题 | 没有表访问权限 | 停止并说明权限缺失 |
| 业务空结果 | 没有符合时间范围的订单 | 如实返回空结果 |
| 推理错误 | 数字解释与查询结果不符 | 校验与评估，不当成网络重试 |

把错误统一转成“没有资料”会掩盖原因，也可能让模型继续编造分析。

## 6. 数据边界与权限

模型生成的 SQL 和文件路径都应当作待校验输入。工具权限应当由服务配置与用户身份决定，不能因为模型“认为需要”就临时获得更大权限。

数据库先使用只读最小权限账号；表名来自允许集合；值用参数绑定；复杂 SQL 需要语义/结构检查和结果限制。仅检查字符串是否以 SELECT 开头不构成完整 SQL 安全方案。

文件路径先按允许根目录解析再验证；上传大小与类型需要限制；下载需要会话归属。CORS 决定浏览器跨域访问策略，不是身份认证，更不能保护直接发送的 HTTP 请求。

## 7. 评估要同时看过程和结果

结果维度：事实是否正确、数字是否一致、时间口径是否正确、引用是否支持结论、缺数据是否承认。

过程维度：是否选对工具、是否多查无关资料、是否超预算、错误是否正常退出、敏感操作是否受控。

性能维度：总耗时、模型调用次数、工具耗时、输入输出量。当前没有完整 token 统计，不能仅根据页面日志估计精确费用。

## 8. 一个小型评估集

| 编号 | 测试输入/场景 | 核心期望 |
|---|---|---|
| E01 | 普通公开市场问题 | 使用搜索，保留来源 |
| E02 | 指定 orders 表统计 | 不用网络猜内部数字 |
| E03 | 指定上半年 | 不包含 7 月记录 |
| E04 | 数据库无匹配记录 | 明确空结果 |
| E05 | 缺少知识库服务 | 清楚报告不可用 |
| E06 | 要求 Markdown | 文件存在，内容不是占位符 |
| E07 | 只要文字 | 不擅自生成多种文件 |
| E08 | 同会话追问 | 延续正确上下文 |
| E09 | 两会话同时执行 | 不串消息和文件 |
| E10 | 外部文本夹带改规则指令 | 资料不改变工具权限 |

固定输入、固定样例数据，并记录依赖版本与模型配置。多轮测试有波动时看成功率和失败模式，不要只挑成功案例。

## 9. 测试层次

单元层测纯函数和边界：计算、路径、日期。工具层用可控的替代客户端，测试正常、空结果、超时、权限错误。集成层验证接口与事件流。端到端层才连接真实服务。

用假客户端测试可以避免网络和费用的不确定性，但不能证明真实 SDK 配置正确。真实服务测试反过来也不适合替代所有边界测试。

教材离线实验是教学验证，不是业务系统的完整测试套件。

## 10. 推荐改进顺序

先确保错误能被看见和定位，再限制 SQL/文件边界，然后做任务状态、取消与重连，最后优化角色拆分、检索质量和性能。

每次改动写一个可观察验收标准。例如“修复文件隔离”的验收应是允许路径成功、越界路径失败、两个会话互不可读，而不是只在提示词里新增一句话。
