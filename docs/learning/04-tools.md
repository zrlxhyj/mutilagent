# 04：工具设计、输入输出与错误处理

[上一章](03-prompts-context.md) · [目录](README.md) · [下一章](05-multi-agent.md)

## 1. 工具是模型与现实操作之间的接口

一个好工具应回答五个问题：什么时候使用；输入是什么；具体做什么；返回什么；失败如何表示。只写一个功能强大的函数而没有清楚的说明，模型仍可能不会正确调用。

LangChain 的 `@tool` 根据函数定义构建工具信息，类型注解参与参数结构，docstring 提供用途说明。参考 [官方工具文档](https://docs.langchain.com/oss/python/langchain/tools)。本章的具体函数行为以项目源码为准。

## 2. 项目显式定义的九个工具

| 工具 | 所属角色 | 输入 | 主要输出/副作用 |
|---|---|---|---|
| `internet_search` | 市场情报 | 关键词、主题、条数等 | Tavily 返回结果 |
| `list_sql_tables` | 数据分析 | 无 | 表名文字 |
| `get_table_data` | 数据分析 | 表名 | 前 100 行的简化 CSV 文本 |
| `execute_sql_query` | 数据分析 | SQL | 查询结果文本 |
| `get_assistant_list` | 内部知识 | 无 | RAGFlow 助手说明 |
| `create_ask_delete` | 内部知识 | 助手名、问题 | 回答并删除临时会话 |
| `read_file_content` | 主智能体 | 文件名、instruction | 提取文本或表格概况 |
| `generate_markdown` | 主智能体 | 内容、文件名、路径 | 写入文件并返回消息 |
| `convert_md_to_pdf` | 主智能体 | 输入与输出文件名 | 转换 PDF |

这是仓库显式编写的工具数量；框架可能注入额外工具。README 中旧的“8 个工具”不应用来代替实际枚举。

## 3. 精读 internet_search

调用顺序：

```text
模型提供参数
→ 工具入口
→ monitor.report_tool 上报开始事件
→ _search_with_retry
→ tavily_client.search
→ 返回结果给框架
```

`query` 决定搜索词；`topic` 在代码声明的选项中选择；`max_results` 默认 5；`include_raw_content` 默认 False。

参数写成 `int` 并不自动保证处于合理范围。例如负数、过大的数值，需要额外边界校验。`Literal` 给出了枚举信息，但外部服务支持范围也需要与 SDK 和 API 对齐。

`monitor.report_tool` 在执行搜索之前调用。因此页面显示“开始执行工具”只证明进入了工具，不能证明搜索成功。

## 4. 重试到底做了几次

[utils/retry.py](../../utils/retry.py) 使用：

```python
for attempt in range(max_retries + 1):
    ...
```

当前搜索配置 `max_retries=3`，意味着首次尝试加三次重试，共最多四次请求。等待大约是 1、2、4 秒，实际总耗时还要加上每次网络请求耗时。

注释说“超时 30 秒”，但客户端创建和 search 调用没有在这里显式传入该参数，不能把这条注释当作项目已经设置的超时保证。SDK 可能有自身默认值，应检查安装版本。

当前捕获 `Exception`，范围很宽。凭证错误、参数错误通常不值得原样重试；临时网络故障更适合重试。进一步可以区分错误类别、增加随机抖动，并设置整个任务的时间预算。

这层装饰器是同步包装，等待用 `time.sleep`。不要直接给异步函数套用它并期待正确等待协程；异步版本应 await 函数并使用 `asyncio.sleep`。

## 5. 返回结果应让模型容易理解

当前工具返回值有字符串、SDK 对象/字典等不同形式。字符串实现简单，但“查询失败”和“没有数据”容易混在一起。

改进示例，尚未接入：

```json
{
  "ok": true,
  "data": [{"category":"数码电子","amount":"29895.00"}],
  "source": "orders",
  "row_count": 1,
  "truncated": false,
  "error": null
}
```

字段名称不是标准协议，只是一种设计。关键是明确成功、数据、来源、截断和错误。对于金额，应约定单位、精度和表示方式。

失败时可返回明确的错误类别；如果抛异常，则要清楚由哪层捕获。不要既吞掉异常，又让上层把错误字符串当成成功资料。

## 6. 参数契约不能只有说明

`read_file_content` 接收 `instruction`，但当前实现只把它用于监控参数，没有据此动态执行“提取摘要”或“统计全部销售额”。因此接口看似接收了指令，实际功能没有完全实现。

`execute_sql_query` 的 docstring 提到最多 100 条，但实现直接 `fetchall()`，未统一添加行数限制。注释不能产生运行时约束。

`get_table_data` 说明必须先列出表，但工具内部没有记忆“前一步是否已经执行”。如果必须保证顺序，需要代码维护状态或在工具内校验。

## 7. 副作用与幂等性

纯计算通常重复执行不会改变外部世界；写文件、创建会话、修改数据库则有副作用。

幂等性描述同一操作重复执行后是否产生等价的最终效果。写同名同内容文件可能覆盖已有内容；发送两次支付请求则可能造成重复扣款。即使本项目没有支付工具，也应从现在理解“重试副作用操作需要额外设计”。

RAGFlow 提问工具先创建临时会话。如果后面提问失败，当前删除操作不会执行，因为它未放入独立 finally 清理路径。这是资源生命周期问题，可作为改进练习。

## 8. 新工具的设计清单

先写下名称、用途、参数类型和边界；明确正常与失败返回；说明是否联网和是否修改外部状态；列出三个正常输入与三个边界输入；最后才注册进智能体。

先单独调用工具验证，再让模型选择工具。这样能区分“工具本身坏了”和“模型没有正确选择工具”。
