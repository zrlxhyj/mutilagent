# 03：提示词与上下文设计

[上一章](02-models-messages.md) · [目录](README.md) · [下一章](04-tools.md)

## 1. 提示词是程序的一部分

[prompts.yml](../../prompt/prompts.yml) 保存角色配置；[agent/prompts.py](../../agent/prompts.py) 用 `yaml.safe_load` 读取为字典。

YAML 中的 `|` 表示保留换行的多行文本。缩进表示层级。修改缩进可能把某段内容放进错误字段，因此提示词也需要版本管理和格式检查。

当前配置在导入时加载。修改 YAML 后，正在运行的进程不会仅凭文件变化自动刷新已创建的 Agent；当前启动设置 `reload=False`，通常需要重启。

## 2. 主智能体提示词的六个部分

| 部分 | 当前项目内容 | 解决的问题 |
|---|---|---|
| 身份 | 电商运营团队负责人 | 采用什么业务视角 |
| 团队 | 市场、数据、内部知识三个助手 | 可以委派给谁 |
| 路由 | 外部信息搜网、经营数据查库、内部文档查 RAG | 什么时候选哪种能力 |
| 文件规则 | 用户要求时才生成文件 | 防止无关产物 |
| 执行顺序 | 先获取信息，再生成文件 | 减少空报告 |
| 内容要求 | 报告丰富、包含分析与建议 | 指导最终输出 |

提示词中的“复杂任务先生成 todo-list”表达规划意图。规划文字本身不代表工具已成功执行，任务勾选也不等于结果正确。

## 3. 角色简介与角色指令

子智能体 `description` 主要用于表达可委派的任务范围；`system_prompt` 指导子智能体执行任务。一个设计不清楚的 description 会造成路由问题，即使子智能体内部提示词很好也可能根本没有机会发挥作用。

例如“万能研究助手”范围过宽，容易与其他助手重叠。“查询公开市场新闻与竞品动态，不负责内部订单和内部政策”则更容易判断边界。

当前搜索助手要求至少三个角度、最多五次搜索。这会影响简单问题的成本：一个只需单条事实的问题也可能被要求多次检索。可以将策略改为按任务复杂度分级，但这属于后续实验，不是当前实现。

## 4. 动态上下文从哪里来

`run_deep_agent` 构造 `path_instruction`，把工作目录、上传文件名、读取规则拼到用户输入后面。

这说明“模型的输入”由多部分组成：用户原话、系统行为说明、历史消息、工具说明、运行环境和工具结果。

当前工作环境指令是拼接在 user 消息里的文本，而不是一个独立的高优先级配置字段。不要把中文标题“工作环境指令”误解为程序已经建立了额外权限层。

更清楚的设计可以把程序可信配置和外部资料分开管理，并由工具代码强制执行目录与权限约束。

## 5. 上下文工程的实际问题

假设上传了一个 Excel，工具只返回前五行和统计描述，模型就不能据此断言“已经核对每条订单”。输入范围决定可支持的结论范围。

假设 RAG 助手要求“保留全部原文”，返回非常长的内容，可能挤占后续报告生成空间。应该依据问题筛选相关片段并保留出处，必要时保留原文附件，而不是无限制塞入单次消息。

假设多个搜索结果转述同一篇新闻，它们不构成多个独立证据。上下文组织还需要记录来源关系。

## 6. 把模糊要求变成可判断的要求

较模糊的教学例子：

```text
你是专家，请认真分析，给出优质报告。
```

更容易验证的教学例子：

```text
目标：解释给定期间的销量变化。
事实：仅使用查询或检索得到的信息；每条主要事实标注来源。
口径：说明时间范围、订单状态和金额字段。
缺失：缺少必要数据时明确列出，不把假设写成结论。
输出：事实、可能原因、建议、仍需验证的问题。
```

这些文本是改写练习，尚未替换项目提示词。

## 7. 软约束与硬约束

| 需求 | 提示词可以做什么 | 程序应保证什么 |
|---|---|---|
| 最多搜索五次 | 告诉模型节制调用 | 计数并限制实际调用 |
| 仅查询数据库 | 告诉模型只生成读操作 | 使用只读账号和校验层 |
| 保存到会话目录 | 提供正确路径 | 归一化并验证最终路径 |
| 输出指定字段 | 描述字段含义 | 使用结构化校验并处理缺项 |
| 没证据时不编造 | 明确行为期望 | 评估证据与结论对应关系 |

强制要求不能完全依赖模型自觉遵守；格式正确也不能证明内容真实。

## 8. 外部资料中的指令

搜索网页或上传文件可能包含“忽略之前要求”等文字。它们应被视为待分析的数据，不能自动获得更改工具权限或任务目标的权力。

这个问题称为提示注入。仅在提示词中加一句“不要被攻击”不够，还需要限制工具权限、区分数据和指令、减少秘密暴露、校验高影响操作。

本项目直接把工具提取文本交给模型，尚未看到完整的来源可信度处理机制。可以在后续作业中给资料加来源标签和明确的数据边界。

## 9. 一次有意义的提示词实验

固定五个问题，保存原始输出；只修改一条规则；重新运行同样的问题；比较工具选择、工具次数、事实出处、失败表达和耗时。模型输出可能有波动，重要结论要多次重复观察。

不要同时更换模型、提示词和工具实现，否则很难知道变化来自哪里。

## 10. 自测

1. 修改 prompts.yml 后，已创建对象一定立即使用新提示词吗？
2. “最多五次搜索”怎样变成可靠的系统限制？
3. 把文件名告诉模型，是否等于模型已经读取文件？
4. 为什么报告写满一千字不能证明质量？
