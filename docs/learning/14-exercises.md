## 作业 A：画出一次执行过程

**目标**：不用运行系统也能解释职责。

从 sendTask 开始，依次找到 createSession、run_task、run_deep_agent、create_main_agent、internet_search、monitor._emit、ws.onmessage。

给每个节点标注输入与输出，再用不同颜色区分控制流、工具数据和监控事件。特别标出“工具开始事件”和“工具实际返回”的区别。

**验收**：你能解释 HTTP 为什么不返回最终报告，为什么 monitor 负责展示而不是决策，以及子智能体是谁真正执行的。

## 作业 B：理解最小 Agent 循环

运行实验 01。先不改代码，手工写出每一步 messages 增加了什么。

把模拟销售额从 120 改成 80，预测最终增长率再运行。尝试把工具名改为不存在的名字，观察控制层如何拒绝调用。不要用 eval 把模型字符串当任意 Python 执行。

**验收**：最终结果随工具数据变化；你能指出决策器、执行器和消息列表各自所在位置。

## 作业 C：给项目增加一个确定性工具

**目标**：从普通函数到 Agent 工具。

新建 `tools/growth_tools.py` 的教学示例：

```python
import math
from langchain_core.tools import tool

@tool
def calculate_growth(current: float, previous: float) -> dict:
    """计算相对上一期的增长百分比。

    仅用于已确认的非负业务数值；previous 必须大于零。
    返回 percentage，例如 20.0 表示增长 20%。
    """
    if not math.isfinite(current) or not math.isfinite(previous):
        return {"ok": False, "error": "输入必须为有限数值"}
    if current < 0 or previous <= 0:
        return {"ok": False, "error": "current 须非负，previous 须大于零"}
    return {
        "ok": True,
        "percentage": round((current - previous) / previous * 100, 2),
    }
```

先单独 `.invoke({"current":120,"previous":100})`，再测试零、负数和无穷大。随后在 `create_main_agent` 的 tools 列表中加入工具对象，并明确提示词中的使用范围。

注意：金额计算在实际财务场景应使用合适的十进制表示和舍入规则；这里的 float 示例用于理解工具接口。

**验收**：正常结果为 20.0；非法输入有明确失败结果；模型确实调用工具，而不是只凭文字说“使用了工具”。

## 作业 D：比较单工具与子智能体

在作业 C 基础上，定义一个仅配备增长计算工具的“指标计算助手”。配置 name、description、system_prompt、tools，再加入主智能体 subagents。

使用同一个简单问题，对比“主智能体直接用工具”和“先委派计算助手”的日志、调用次数和耗时。

**验收**：能解释多一层角色带来的收益或额外开销。若没有收益，应允许保留简单结构，而不是为了多智能体而增加角色。

## 作业 E：提示词对照实验

固定五个问题：单条事实、开放研究、数据库统计、知识库缺失、要求文件。先记录原版结果。

只把搜索策略改为“根据任务复杂度决定次数，简单事实优先一次检索，证据不足再补充”，然后重复运行。

**记录**：是否选对工具、搜索次数、来源质量、回答完整度、错误表达、耗时。外部搜索结果本身会变化，要在笔记里说明这一限制。

**验收**：至少列出一个改善案例和一个未改善或退化案例，而不是只展示成功输出。

## 作业 F：真正的多轮会话

第一步用同一个 thread_id 提交两轮问题；第二步换新 ID 重复第二轮；第三步比较结果。

然后设计前端两个不同操作：“发送新任务”生成新 ID；“继续当前会话”复用当前 ID。对于同 ID 尚未结束的任务，明确排队或拒绝策略。

**验收**：第二轮能延续必要历史，新 ID 不误用旧会话数据；页面刷新是否恢复，应单独声明，不能混为一项能力。

## 作业 G：文件边界

先运行实验 03 理解原理，再为业务路径函数设计测试：普通相对路径、子目录、父目录跳转、绝对路径、另一个会话路径、带特殊字符的文件名。

改进时同时检查上传、读取、生成、下载四个入口。只修一个工具不能保证整个应用都受保护。

**验收**：允许的路径正常工作；越界请求明确失败；已有合法文件不被意外覆盖；用户 A 不能读取 B 的文件。

## 作业 H：可观察的运行生命周期

增加 run_id、工具结束事件、耗时和统一终态。让前端显示“模型等待”“工具运行”“已完成”“失败”等有证据的状态。

模拟：工具正常、工具返回空结果、工具抛异常、网络超时、文件写入失败、WebSocket 断开。

**验收**：能根据日志判断失败阶段；开始事件不会被当成成功；每次运行最终有确定状态或可查询的未完成状态。

## 作业 I：综合小项目

目标：制作“样例店铺月度分析助手”。限定使用测试订单库和公开信息，产出包含数据口径、关键数字、来源、建议和不确定性的 Markdown。

按以下顺序实施：固定数据与问题 → 单独验证 SQL → 验证搜索工具 → 明确助手返回格式 → 组装主智能体 → 增加文件输出 → 做评估集。

**交付物**：功能说明、架构图、十条测试案例、一次完整执行记录、一份报告、已知限制。

**验收**：数字可复算；上半年不会混入 7 月；搜索失败时不伪造来源；用户不要求文件时不多生成；报告路径在指定目录；重复运行不会无意破坏已有数据。

## 评分标准

| 维度 | 分值 | 观察证据 |
|---|---:|---|
| 能解释执行机制 | 20 | 消息与调用流程图 |
| 工具输入输出清晰 | 20 | 参数校验与失败返回 |
| 事实和计算正确 | 20 | SQL、手算和引用核对 |
| 失败可诊断 | 15 | 日志、终态与错误类别 |
| 数据边界明确 | 15 | 路径与权限测试 |
| 实验可重复 | 10 | 固定样例与配置记录 |

达到 80 分且能说明剩余限制，比完成更多角色配置更能体现开发能力。
