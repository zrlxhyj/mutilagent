# 10：网络搜索、SQL 与 RAG

[上一章](09-state-memory.md) · [目录](README.md) · [下一章](11-files.md)

## 1. 先判断问题需要哪类事实

| 问题 | 优先信息源 | 理由 |
|---|---|---|
| 某行业最近发生了什么 | 网络搜索 | 外部公开动态 |
| 店铺上半年卖了多少钱 | MySQL | 精确结构化业务记录 |
| 公司退款审批规则是什么 | 内部知识库 | 企业专属文档 |
| 这份上传文件说了什么 | 文件读取 | 用户明确提供的资料 |

把内部销售额拿到网络上搜，通常得不到可靠答案；把政策文档当成普通订单表查询也不合适。路由首先是数据来源问题。

## 2. 搜索链路精读

[tavily_tool.py](../../tools/tavily_tool.py) 创建客户端并执行 search。结果回到市场情报助手，再由它提供给主智能体。

搜索质量取决于关键词、时间范围、来源覆盖与结果核验。搜到一个页面不等于页面内容真实；页面提到某年份，也不等于新闻就在该年份发布。

建议记录标题、链接、发布时间、支持的事实与检索时间。项目当前没有统一的来源结构和引用核验层，可以将其作为改进作业。

“至少三个角度”主要增加覆盖范围，不自动保证三个独立来源。不同网站转载相同材料仍可能只有一份原始证据。

## 3. SQL 从零理解

表可以理解为按列组织的记录集合。`orders` 是订单表，字段包括 category、price、quantity、total_amount、status、created_at。

常见查询：

```sql
SELECT category, SUM(total_amount) AS sales_amount
FROM orders
WHERE status = 'completed'
  AND created_at >= '2026-01-01'
  AND created_at < '2026-07-01'
GROUP BY category
ORDER BY sales_amount DESC;
```

SELECT 选择结果；FROM 指定表；WHERE 过滤；SUM 求和；GROUP BY 按品类聚合；ORDER BY 排序。上面的时间条件表示完整上半年，使用左闭右开范围，避免误漏 6 月 30 日的非零时分秒。

业务金额用哪个字段很重要。`SUM(price)` 没有考虑数量；`SUM(total_amount)` 才符合当前示例表的金额字段语义。实际系统还可能有退款、折扣、税费，必须先明确口径。

## 4. 三个数据库工具如何配合

`list_sql_tables` 执行 show tables，告诉模型实际表名。`get_table_data` 执行限定 100 行的 select，提供字段和样例。`execute_sql_query` 接收模型生成的 SQL 并直接执行。

当前 get_table_data 使用字符串插入表名，并未建立表名白名单；execute_sql_query 未实施只读限制；配置启用了 autocommit。因此学习时应使用专门的测试库和只读账号，不能把“查询”这个工具名称当成权限保证。

返回结果用逗号拼接，不是完整 CSV 编码：如果单元格包含逗号或换行，文本可能歧义。改进可使用 csv 模块或结构化行数据。

## 5. 用仓库样例手算验证

[sql/init.sql](../../sql/init.sql) 包含八条示例订单。假设只初始化一次、没有其他记录，数码电子金额为：

```text
8999 + 10499 + 3598 + 6799 = 29895
```

前三条属于上半年，金额为 23096；最后一条在 7 月，不在上半年范围。

这些是示例记录的算术结果，不是实际业务结论。重复手工执行 INSERT 可能重复插入，因为 order_no 没有唯一约束；因此真实数据库查询结果要与当前数据核对。

实验 [04_sql_grounding.py](examples/04_sql_grounding.py) 用内存 SQLite 和缩小的模拟订单集演示日期、数量和参数化条件。它不连接 MySQL，也不是完整执行 init.sql。

## 6. RAG 的基本原理

RAG 是检索增强生成：先找相关资料，再让模型依据资料回答。一个常见完整流程包括文档解析、切分、索引、检索、重排、构造上下文和生成答案。

Embedding 把内容映射成数值向量，便于按某种相似性比较。向量相似不等于事实一致，也不直接证明答案正确。关键词检索、向量检索和混合检索可以服务不同需求。

切片过小可能丢上下文，过大可能引入无关信息；重排可以重新评估候选片段相关性。这些都是后续学习方向，当前仓库没有本地实现完整流程。

## 7. 本项目的 RAGFlow 接法

[ragflow_tools.py](../../tools/ragflow_tools.py) 先 list_chats 获取助手列表，然后按名字选择助手、创建临时 session、调用 ask、读取流式结果、删除会话。

这里查询的是“聊天助手”，并通过它关联的知识库获取回答，不是直接对本地向量表执行查询。读取到的是外部服务生成的回答，仍需要关注它的引用和依据。

当前用 `chats[0]` 选择第一个匹配结果。没有匹配会产生异常并返回错误文字；多个同名结果也没有消歧流程。

流处理使用 `result = part.content`，保留最后一段，而非逐段拼接。它假定最后一次 content 包含最终累计内容；若更换 SDK 或响应模式，需要核对是否仍成立，不能不加判断地改成 +=。

## 8. 信息汇总应保留什么

一个事实应尽量包含“值、时间、范围、来源”。例如“数码电子收入 29895”缺少数据范围；“示例 orders 表全部八条记录中，数码电子 total_amount 合计 29895”更可验证。

建议将最终内容分为已确认事实、合理推断和待验证假设。销量下降与竞品促销同时出现，只能形成解释线索，还不能证明全部下降都由竞品造成。
